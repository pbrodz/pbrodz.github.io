Case Study

From EF Core to Dapper — Proving the Migration with Load Tests

The payments API's hot paths were spending a growing share of request time inside EF Core's query translation and change-tracking overhead. Rather than rewrite the data-access layer on a hunch, I built the case for a Dapper + stored-procedure migration with a controlled load test first, then confirmed it against real staging and production traffic before calling it done.

Controlled baseline: k6 load test

Single endpoint (/zero/validate), 10 virtual users, 30 second duration, p95 < 500ms threshold, run locally against both implementations back to back.

MetricEF CoreDapper + sprocsDelta
Throughput167 req/s323 req/s+93%
Avg latency59.4ms30.6ms−49%
Median latency50.4ms27.1ms−46%
p90 latency67.6ms40.3ms−40%
p95 latency78.7ms45.7ms−42%
Min response22.3ms12.4ms−44%
Max response1,410ms1,230ms−13%
Iterations (30s)5,0139,697+93%
Failed requests00—

Zero failures on either side — this was purely a latency and throughput story, not a stability fix. Twice the traffic at roughly half the latency, for the same 10 VUs.

What Dapper actually fixed

EF Core generated anywhere from 3 to 13 sequential SQL calls per request depending on runtime state. Dapper replaced that with a fixed 7–8 calls, 3 of which run in parallel — which is what eliminated the tail latency spikes, not just the average case.

Confirming it in staging, on real traffic

Local benchmarks can flatter a change, so I re-ran the comparison against actual staging traffic across both endpoints (East US → West US 2, ~70ms round trip):

EndpointStateP50P75P90P95SQL calls
/zeroBefore (EF)1,4341,8682,4693,2293–13
/zeroAfter (Dapper)1,0971,6752,2852,4238, fixed
/zero/validateBefore (EF)1,8192,2392,8855,4854–13
/zero/validateAfter (Dapper)1,1041,4882,0422,3697, fixed

/zero: −24% median, −25% at p95 (107→183 sampled requests). /zero/validate was the biggest win: −39% median, −57% at p95 (28→85 sampled requests) — the tail latency EF Core produced under its worst-case query pattern is exactly what disappeared.

Production, so far

/zero held roughly steady on median (~2ms round trip to a co-located SQL instance leaves little room to improve) but still cut p95 by 18% and p99 by 43%, with SQL calls capped instead of variable. /zero/validate doesn't have enough production traffic yet to draw a real conclusion — staging is the stronger signal for that endpoint for now.

Extending the pattern: the /unlock endpoint

A teammate had already profiled /unlock's read phase at roughly 340ms sequential — content lookup (~70ms), pass check (~70ms), and a slow Scu.Find call (~200ms) backed by 3–4 EF queries. Moving that path to Dapper cut it to 70–140ms depending on scenario, without touching the write path:

ScenarioTimeSaving
lssk present (common path)~70ms−270ms
No lssk (content + pass parallel, then Scu)~140ms−200ms
Already unlocked (parallel reads, no EF)~70ms−270ms

What's next

  • With SQL overhead cut this much, roughly 85% of remaining request time on production is now inside .NET middleware — auth, CORS, validation. That's the next thing to profile.
  • Before treating Dapper as the default going forward, I'm testing EF Core with AsNoTracking as a lighter-weight alternative, on a teammate's suggestion — my working hypothesis is it recovers maybe 20–30% of the gap, not the full win, but it's worth ruling out before adding a second data-access pattern to the codebase permanently.
